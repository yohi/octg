# OCTG Production CPU-Gate Release Safety Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Plan a verifiable temporary Deno/Worker Production deployment HOLD across both current and historical GitHub Actions entrypoints while Issue #121's Stage 1/Stage 2 rollout prerequisites remain unproven, and hand off any eventual HOLD lift to the separately reviewed staged rollout plan.

**Architecture:** Use two distinct controls: (1) current-ref producer/reusable Workflow definitions fail closed for all trigger types, and (2) an explicitly owner-authorized **cutover** independently closes or contains preexisting/in-flight/waiting jobs, dispatchable historical refs, historical reusable callers and Production Environment/credential access. Static Workflow tests prove only (1); `HOLD_ACTIVE` requires evidence for **both**. Preserve offline validation, Preview-only isolation and existing Production traffic; do not create an alternate deploy path. The eventual HOLD lift belongs exclusively to the existing Issue #121 Tasks 9–12, with separate executable release-gate tests and runtime authorization.

**Tech Stack:** GitHub Actions YAML, Node.js >=22 `node:test`, shell contract tests, Wrangler 4.x (verification of CLI construction only; no remote execution in this plan).

**Spec:** `docs/superpowers/specs/2026-10-05-worker-free-cpu-headroom-redesign.md` §§CPU gate, Stage 1, Stage 2/bridge and completion; `docs/superpowers/plans/2026-10-05-worker-free-cpu-headroom-redesign.md` Tasks 9, 10, 11, 12. **Fixed audit baseline:** `0ac76d5727018ee47e01935022d59581039a87d2` (2026-10-27 JST). This is an interim safety delta, not a replacement for the existing Task 9–12 implementation plan.

## Global Constraints

- **HUMAN OWNER DECISION GATE:** Before implementing this temporary hold, approve its operational trade-off: while in force, normal master-push *production deployments of both Deno and Worker stop*. CI validation and separate Preview paths remain. No model may infer this approval from the existence of this plan.

An unprotected/unverified route means `HOLD_CUTOVER_BLOCKED / HOLD_ACTIVE_NOT_PROVEN`.
- **HISTORICAL REF LIMIT:** GitHub Actions `workflow_dispatch`, reusable workflows and previously queued/running/Environment-waiting jobs may use older Workflow definitions. Adding an `if: false` or a failing step to current `master` cannot retroactively secure these. Environment branch restrictions, trusted credentials and existing run states require direct administrative/operator verification and may require separate authorized configuration changes.

- Cloudflare Worker Free target is 10 ms; all required stateless series: `p99 <= 5 ms`, `max <= 7 ms`, `exceededCpu = 0`, >=500 successes each, full platform telemetry. CI tests are not CPU-gate proof.
- Existing auth, Cloudflare/Deno secrets, quota decision semantics, D1 separation, lifecycle rollback and Production/Preview isolation must remain unchanged.
- Do not create a `workflow_dispatch` or Boolean environment variable that bypasses the hold or promotes the candidate to 100% without the approved Stage 2 chain and external/operator authorization.

## Deferred HOLD-Lift Contract — Mode-Scoped Issue #121 Tasks 9–12 (not proved here)

The interim Task 1/2 Workflow tests prove **unconditional denial in updated/current-ref Workflows only**; Task 3 tests prove only runbook wording. Historical-ref cutover remains the independent Task 0 operator gate. This plan **does not** implement or verify a safe HOLD lift. A separate, reviewed Task 9–11 implementation must atomically replace the interim unconditional denial with **mode-scoped** release guards; there is no blanket prerequisite that `bridge 100% / candidate 0%` already exist before `bridge` or `candidate-deployment` can construct that state.

**Common prerequisite for any approved Production mutation mode:** current applicable Human Owner/operator authorization, exact authorized Production account/environment, immutable Task 11 source SHA (with Task 6 Stage 1 re-run from that SHA), candidate version-config fidelity, relevant Task 9 compatibility evidence, and an unambiguous live Production baseline/previous stage. Where a prerequisite belongs only to a *later mode*, do **not** prematurely impose it on an earlier mode. All unfulfilled, stale, mismatched or unverifiable **mode-specific** prerequisites return `BLOCKED / INCOMPLETE` before **that mode's** remote mutation; do not invoke that mode's deploy/secret adapter. Failed post-mutation verification blocks **subsequent** modes, retains the actual observed state, and follows the separately authorized recovery path; it cannot be described as a pre-mutation block.
